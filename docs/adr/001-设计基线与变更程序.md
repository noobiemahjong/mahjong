# ADR-001：设计基线与变更程序

状态：已确认
日期：2026-10-28
相关：docs/DESIGN.md v1.0（D1–D18）

## 背景

`docs/DESIGN.md` 已经把目标、分层、tick 引擎、会话流、回放、观战、重连、部署、测试与里程碑写成 v1.0，并以 D1–D18 记录了拍板结论。

在开工前必须回答三个问题，否则第一行代码之后就会出现「文档写一套、代码做一套」：

1. 谁是设计的权威？
2. 发现设计需要改时，改哪里、谁批准、历史怎么留？
3. ADR 与 DESIGN 如何避免同一信息写两遍？

## 决策

1. **`docs/DESIGN.md` v1.0 是设计基线**：D1–D18 与各章节是当前权威；任何实现都必须能指回其中一条（或指回一条显式收窄它的 ADR）。
2. **变更基线必须走新 ADR**：ADR 必须写明「收窄/替代 DESIGN §x 或 Dn」，并在同一提交内：
   - 更新 `docs/DESIGN.md` 的决策表（状态列加「被 ADR-xxx 收窄/替代」）；
   - 更新 `docs/adr/README.md` 索引；
   - 若改变对外契约，提升 §6.5 的版本三元组并写进后果。
3. **ADR 正文冻结**：已确认的 ADR 不改写；后续决策写新 ADR 并在索引标注关系。
4. **旧 Unity 行为是默认基线**：没有在 `docs/registry/旧版行为偏离登记.md` 登记的行为差异，一律视为缺陷；有登记才是「有意偏离」。
5. **基线版本**：`DESIGN.md` 版本号只在基线级变更时递增（v1.0 → v1.1 …）；ADR 编号独立递增，二者不互相替代。

## 理由

- 单独靠 DESIGN：改起来无痕迹，回看时无法判断某条规则是拍板还是随手写的。
- 单独靠 ADR：几十条决策散落，读不出一个完整设计。
- 二者分工后：DESIGN 给「当前长什么样」，ADR 给「为什么变成这样」，git 给「什么时候变的」。

## 放弃了什么

| 方案 | 否决理由 | 重开条件 |
|---|---|---|
| 用 Issue/Wiki 作为设计权威 | 与代码不同仓、不可离线、评审不可复现 | 团队扩到需要多人并行评审时再评估 |
| 直接改 DESIGN 不留 ADR | 无法追溯，旧结论被静默覆盖 | 不重开 |
| 把 D1–D18 逐条拆成 ADR | 同一信息两份副本，必然漂移；DESIGN 已足够 | 若某条决策需要长论证（>1 页）再拆 |

## 后果

- 任何「设计改了」的提交，diff 里必须同时出现 ADR 与 DESIGN 变更；只有其一的评审直接打回。
- 里程碑任务若发现设计与实现冲突，先写 ADR，再改代码。
- 文档预算：DESIGN 上限 64KB；超出时先判断是「信息该下移」还是「确实需要扩基线」，前者拆文档，后者同提交上调预算并说明。
