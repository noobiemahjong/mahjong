# Agent Note: v1 已否决的设计方案

Status: rejected — v1 设计空间已收敛；保留以防重提

## Problem

v1 开工前讨论过若干方案，需要在实现前固定「不选什么」，避免后续每轮重新论证，或让 agent 把否决方案当新提案重提。

## Decision

以下方案在 v1 明确不采用；重开条件写在表内。

| 编号 | 否决的方案 | 理由 | 重开条件 |
|---|---|---|---|
| R-001 | 继续维护 Unity 旧项目，不重写 | 联网/重连/回放结构性问题无法在旧架构内低成本修复 | Godot 重写被证明不可行（AOT/导出/性能不达标） |
| R-002 | 继续用 Netcode for GameObjects + UGS Lobby/Relay | 强绑定 Unity/场景；重连、观战、回放需另起炉灶；公网依赖云服务 | 自研协议与 VPS 运维成本持续高于云服务，且愿意回到 Unity |
| R-003 | SGS 式「只录玩家视角流 + seed 重建」回放 | 对洗牌算法与内容版本强依赖；格式脆弱；无法稳定做全景 | 回放体积成为硬约束且愿意冻结洗牌算法与内容版本 |
| R-004 | protobuf-net / 反射式序列化 | 客户端 NativeAOT 禁反射序列化；运行期生成不可控 | 放弃 AOT（不预期） |
| R-005 | Godot 内置 MultiplayerAPI / MultiplayerSynchronizer | RPC 绑节点路径；会话/重连/观战/版本校验仍要自研；不适合权威回合制 | 只做局域网且放弃重连/回放时 |
| R-006 | v1 引入 checkpoint/状态快照 | 8 局全量重放 <200ms，收益低；会引入状态序列化与版本兼容负担 | 单局重放 >300ms 或重连体验不可接受 |
| R-007 | 客户端重跑规则做权威/预测 | 隐藏信息泄露；两端流程强耦合；作弊面大 | 不重开；客户端只做镜像与本地预校验 |
| R-008 | v1 做中继/NAT 打洞 | 回合制 + VPS 权威服已解决公网问题；中继增加运维与复杂度 | 玩家无法使用 VPS 且必须「无公网 IP 自开房」 |
| R-009 | 单机单独写一套逻辑 | 会形成「单机好、联机坏」的双路径；测试面翻倍 | 不重开；单机 = 本地 Session + Mirror |
| R-010 | 观战默认全知 | 实时全量观战 = 作弊通道 | 私有房明确开关（默认关） |
| R-011 | 与旧 Unity 版做行为等价、逐项登记差异 | 旧版很多设计不合理；会把实现绑死在旧版，拖慢重写 | 仅当需要复用某条旧规则细节时查旧代码，不建对照表 |

## Alternatives considered

- 每条方案单独一篇 rejected Note：11 篇碎片笔记，检索成本高于收益；v1 阶段合并为一篇，条目满 3 条同类决策时再拆。
- 只写「不采用的方案」不写理由：下个 agent 无法判断是否该重提；理由与重开条件必填。

## Consequences

- 新提案先查本表与 `docs/DESIGN.md`；命中则说明重开条件是否成立，否则不重新论证。
- 条件成立并决定重开时，写新 Note（lifecycle 按新决定），在本表对应行标注「已重开」并链接。
