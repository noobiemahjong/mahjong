# Agent Note: 状态哈希布局 v3（公共揭示区）

Status: implemented — `StateHash.LayoutVersion` 为 3，牌墙之后追加公共揭示区段；空局 53B、富局面 113B，两条金标重录。

## Problem

M0.3 中马把马牌从牌墙移进公共揭示区（`GameState.Revealed`）。v2 布局只编码牌墙与四家，于是「翻马后」与「牌墙少一张、揭示区多一张」的另一个局面会得到同一哈希：对账看不出揭示区的差异，回放重建也无法用哈希校验揭示区。揭示区是公开状态，参与后续展示与审计，必须进哈希；把它混进四家段又会破坏「一区一段」的可对齐性。

## Decision

1. 段位固定：版本 → 牌墙 → 揭示区 → 玩家数 → 四家 → 当前座位 → 局号；揭示区紧跟牌墙，编码与其它区域同形：`u16 张数 + 张数 × u16 tileId`，按槽位序、不排序。
2. 首字节版本由 2 升 3；生产 `StateHash.LayoutVersion` 与测试侧 `StateHashOracle.LayoutVersion` 同批升 3，`Measure` 与 `Write` 同步（先量后写、一次分配）。
3. 两条金标重录（v3）：空局 53B `4f3948a487ab7c2311a2d0d04720b39911f7afdf4b22b098796cc75f655dac05`；富局面 113B `5d4c1af028100b249f80eb14823346df3ccf4c00c19baf1cd33759a28957ab2a`。
4. 旧 v2 两条值保留为 `LegacyV2`（空局 51B `9233ee2f05f8fb737c69c9d271c7ad741cf3e708eef1cc17931597a31e847b6b`、富局面 111B `fc85d25e85af156153c4afab3da475e1f186a31310078bec7131eaddd623edc2`），断言 v3 下不产出旧值，只增不删。
5. `GameState.Deal` 清空揭示区：跨局累积会让同 seed 两次一致假通过，也是 136 张守恒的前提。

## Alternatives considered

- **不动版本、把揭示区并进牌墙计数**：同一哈希分不清「牌在墙里」与「牌已翻开」，对账与回放都判不了翻马是否发生，牌墙顺序语义也被破坏。
- **揭示区放在四家之后**：字节上成立，但公共区与四家交错，独立实现的段对齐更易写错；按「公共牌区相邻」取紧跟牌墙，见 [T-4 §1](../../../../docs/milestones/M0.3/T-4-中马.md#1-翻马流程)。
- **把揭示区并进某座位的手牌段或副露段**：马牌不属于任何座位，混入会污染「手牌槽位序是哈希事实」这条契约。
- **升成并列的 v4 文件格式（两套并存）**：多一条并行维护路径，而布局只有一处，无并存需求。
- **只扩揭示区、不升版本**：旧实现读到更长字节流会按旧布局静默截断，跨实现比对失败的原因不可读。

## Consequences

- 布局是跨实现契约：第三方实现按本 Note 的段位与宽度拼字节即可复现两条新值；v2 实现读到版本 3 必须拒绝，不能猜测。
- M0.2 的旧金标按原值标注、不对应 v3；旧 `.mjr` 按 [replay-format §5](../../../../docs/specs/replay-format.md#5-播放规则) 拒播。
- 字节长随揭示区张数线性增长（每张 +2B），空局与富局面的两条长度作为布局哨兵：布局再改必须重录，不能复用旧值。
- 其余段位与编码口径沿用 [v2 布局](2026-10-29-state-hash-byte-layout.md)，其版本事实行与交叉链接指向本篇；实现见 [StateHash](../../../../src/Mahjong.Core/Flow/StateHash.cs)。
