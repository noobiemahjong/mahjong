# Agent Note: 状态哈希的字节布局

Status: implemented — `StateHash.Compute` 把 `GameState` 的模型字段按固定小端布局编码后取 SHA-256，返回 64 字符小写 hex。

## Problem

回放校验、联机对账与"同输入序列两遍哈希一致"都要求哈希只依赖模型字段，且与 .NET 的反射、序列化细节无关。直接序列化对象时，属性顺序、类型版本、装箱方式都会让不同实现得到不同字节流；把时间、日志、内容清单混进去，同一局面又会因旁路数据不同而分叉。跨实现（C# 服务端与独立脚本）还必须能各自照文档拼出同一段字节。

## Decision

1. 入口是 `Mahjong.Core.Flow.StateHash.Compute(GameState)`：按布局量出精确字节数，一次性分配并写入，取 `SHA256.HashData` 后转小写 hex；不写尾随填充、不加分隔符。
2. 所有整数小端；长度前缀 `u16`；布局版本写在首字节，为 2。
3. 字段顺序固定：版本 → 牌墙（张数 + 槽位序 id）→ 玩家数 → 四家（座位、庄家、分数、手牌、副露、弃牌）→ 当前座位 → 局号。
4. 分数是 `short`，提升为 `int` 后写 4 字节小端补码；副露每副 4 字节头（种类、亮明、目标座位、张数）+ 张数 × `u16` 牌 id，无目标座位写 255。
5. 只编码模型字段：不含时钟、Session、日志、内容清单哈希与规则版本；动作树与请求状态不参与。
6. 牌 id 取 `Tile.Id`（物理牌 1–136）；区域按槽位顺序编码、不排序，zone 的插入顺序因此是哈希事实。

实现见 [StateHash](../../../../src/Mahjong.Core/Flow/StateHash.cs)。

## Alternatives considered

- **`record` 默认输出或 JSON 后哈希**：写得少，但字段顺序与格式随编译器、库版本变化，字符串编码还会把类型细节带进来。
- **反射遍历属性**：属性顺序不保证，AOT 裁剪下不可靠；客户端也禁止反射式序列化。
- **把内容清单哈希与规则版本一并哈希**：看似更全，但同一局面在不同内容版本下会得到不同哈希，掩盖真正的状态分歧；版本匹配属于会话建立阶段。
- **用 `u32`/`i64` 定长字段**：牌 id 与张数天然放进 `u16`，加宽只让字节流更长、跨实现更容易写错。
- **把牌种 `Type` 一起哈希**：牌种可由物理 id 推出，重复编码不增加信息，只多一处可能不一致的来源。

## Consequences

- 独立实现可以只照布局拼字节；Python 与 C# 两侧得到同一 hex，字节流逐字节一致。
- 布局是跨实现契约：改字段顺序、宽度或版本号等于改回放与联机对账口径，必须写新 Note 并同步服务端与客户端。
- 哈希只覆盖局面，不覆盖动作树进度：同一哈希可以对应不同动作树位置，对账只保证局面一致。
- 依赖 zone 只追加（见 [区域/副露 Note](2026-10-29-zone-append-only-and-meld-upgrade.md)）：槽位序即流程序；与 [调度器 seam](2026-10-29-scheduler-seams-and-tick-boundary.md) 相关：哈希在 tick 事务边界之外计算，不由调度器调用。
