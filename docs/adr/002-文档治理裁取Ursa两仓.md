# ADR-002：文档治理与开发思路裁取 Ursa-Server / Ursa-Client

状态：已确认
日期：2026-10-28
相关：根 AGENTS.md、docs/AGENTS.md、docs/adr/001

## 背景

`E:/learn/Ursa-Server` 与 `E:/learn/Ursa-Client` 是两套已跑通的 vibe coding 仓库：前者有 49 篇 ADR、纪律路由表、doc budgets 与门禁测试；后者有 AGENTS 子树、doc-gate、CI、里程碑 master/任务形态、MCP 硬门禁。

麻将项目规模小得多（单人主导、Godot + C#、规则/回放/联网三条主线），**只借鉴治理与开发方式，不继承它们的基线**。

> 明确非目标：**不与旧 Unity 版本做行为等价**；**不登记旧版行为偏离**；**不记录代码出处/逆向地址**。旧项目、`docs/notes/`、`docs/ARCHITECTURE-unity-legacy.md` 只作素材与规则参考。

## 决策

### 1. 采用的治理机制

| 机制 | 来源 | 处理 | 麻将版调整 |
|---|---|---|---|
| 根 `AGENTS.md` + 子树 `AGENTS.md` + 读序/冲突裁决 | 两仓 | **保留** | 目前只有根 + `docs/`；`src/`、`tools/` 落地时再建 |
| 三载体分工（注释/commit/docs） | 两仓 | **保留** | 注释只写「为什么/契约/约束」；不写出处、不写行号、不做旧版对应 |
| `docs/` 是项目状态唯一权威 | 两仓 | **保留** | DESIGN/TABLES 为常设文档；旧项目资料降为参考 |
| ADR（一条一决策 + 索引 + 冻结 + 收窄指针） | 两仓 | **保留** | 模板 + 种子 ADR；不追求篇数规模 |
| rejected-alternatives | 两仓 | **保留** | 记录我们否决的设计方案与重开条件（不涉及旧版对照） |
| 里程碑 master + 任务文档 + 状态唯一权威 | Ursa-Client ADR-014 | **保留** | 状态只在任务表；入口 README 不写进度 |
| pitfalls 编号篇（现象/根因/正确做法/验证） | 两仓 | **保留** | 归入 `docs/engineering/pitfalls/`；只写仍有效结论 |
| bugs 与决策/坑分家 | 两仓 | **保留** | 事故诊断单独放 |
| reference 证据链（复现命令/路径） | Ursa-Client | **保留** | 只放技术证据（AOT、表格式、性能、外部资料勘察） |
| 文档预算 + 棘轮 | Ursa-Client ADR-010 | **保留但粗粒度** | 按类别给上限，不做逐文件 census；M0 起冻结 |
| doc-gate（G1–G11）+ commit-msg hook + CI | Ursa-Client ADR-011/017 | **保留为 M0 交付** | 当前只有规范（根 AGENTS §6），**未实现前不声称已跑** |
| 验证分层 L1/L2/L3 | 两仓 | **保留** | L3 改为「AOT 冒烟 + 金标回放」 |
| Conventional Commit + 一任务一提交 + 不 push + 收尾汇报 | 两仓 | **保留** | 标题 ≤50 字、body ≤10 个非空行 |
| MCP 优先（Godot 硬门禁 / Roslyn 可降级） | Ursa-Client ADR-012/020、Server ADR-020 | **保留** | 麻将只有 Godot + C# 两条通道；数据表用仓库内工具/实读 |
| 团队单元化（任务书/写作用域/Lead 复核） | Ursa-Server ADR-048 | **保留精简版** | 一单元一产物、≤80 步/150K、批次 ≤8、同时 ≤5 |

### 2. 采用但不机械化的开发思路

1. **内核与引擎分离**：规则/流程/协议是纯 C#（`Mahjong.Core`），Godot 只做宿主与表现；内核可单测、可换引擎。
2. **先取证/先 spike，再承诺**：AOT、导出、表格内存、tick 性能先做小实验，拿数字再进计划。
3. **设计先行、基线唯一**：先改 DESIGN/ADR，再写代码。
4. **小步可验收**：一任务一提交；每个任务有明确 L1/L2/L3 验收。
5. **量测优先**：性能/内存/体积先测基线再优化。
6. **任务单元化**：单单元一产物，做完停下汇报。
7. **文档只留决策、契约、结果**：过程叙述不落盘。

### 3. 明确不采用

| 不采用 | 原因 |
|---|---|
| 旧 Unity 行为等价 / 旧版差异登记表 | 旧版很多设计不合理；我们按 DESIGN 重新设计，不做逐项对照 |
| 代码出处/逆向地址锚点（IDA 地址、旧版行号） | 对维护无帮助，且把实现绑死在旧版；注释只写契约与理由 |
| Java/官方客户端基线、submodule、脚本转换工具链 | 不适用；旧项目是只读素材 |
| 49 篇 ADR 的规模 | 按需写；ADR 只在「改变基线或不可逆选择」时新增 |
| GitHub Milestone/Issue 镜像 | 单人阶段收益低；需要外部协作再评估 |
| red-test/变异台账、doc-slim 全量普查、逐文件预算 | 维护成本 > 收益；M2 之后再评估 |
| 客户端逆向目录 / 逆向证据链 | 无此工作面 |

## 理由

1. **只保留有判别力的机制**：三载体、ADR、pitfalls、rejected-alternatives、milestones、预算与门禁都能直接防止漂移/失忆/重复；census/变异台账在小仓里成本高于收益。
2. **门禁后置**：M0 没有代码与文档规模，先实现 doc-gate 会阻塞开工；规范先立、工具在 M0 收尾前补齐，未实现就写「待实现」。
3. **不绑旧版**：旧版是素材来源，不是验收标准；我们的节奏由 DESIGN 与里程碑决定。

## 放弃了什么

| 方案 | 否决理由 | 重开条件 |
|---|---|---|
| 完整复制 Ursa-Server 治理（49 ADR + 19 纪律 + 全量门禁） | 治理成本压过开发；多数规则针对大仓/多人 | 团队 >3 人且里程碑并行 >4 时再评估 |
| 不做治理，只写 DESIGN | 决策失忆、重复踩坑、协议契约漂移 | 不重开 |
| 把所有规则塞进根 AGENTS.md | 单文件膨胀、子树无法按需加载 | 不重开；按子树拆分 |
| 与旧 Unity 版做行为等价与差异登记 | 旧版不合理处多；会把新实现绑死 | 仅在需要复用某条旧规则细节时查旧代码，不建对照表 |

## 后果

- M0 必须交付：doc-gate（G1–G11）、commit-msg hook、CI（构建 + 单测 + 文档门禁，无 paths 过滤）。
- 预算与门禁规则已写在根 AGENTS §6；实现前不得作为验收证据。
- 若治理成本开始压过开发（例如每周维护文档 >2 小时），按本 ADR 的「不采用」清单继续收窄，而不是加规则。
