# Lead 工作标准（与任务内容无关）

> 用法：把本文件交给「作为 Lead 的那个会话」，再填 §1 的任务卡；其余按本仓口径执行，不按本文件改写仓库规矩。
> 本文件不含里程碑、批次号或产物名——一律从 §1 指向的文档读取，不由用户或 Lead 手抄。

## 0. 适用范围（任何任务类型；**不预设「写文档」**）

本标准适用于文档撰写、代码实现、缺陷修复、重构、数据整理、配置/规格定稿、调研取证等**任何批次**。

文中「产物 / 交付物」= 该批的唯一交付结果，可以是一份文档、一个模块与测试、一组配置、一张数据表、一份规格。**产物形态由目标文档规定，本标准不预设形态，只规定过程与质量判据。**

| 本标准用词 | 文档任务里 | 代码任务里 | 数据/配置任务里 |
|---|---|---|---|
| 交付形态 | 章节结构 | 模块与文件布局 | 表与字段 / 键与取值 |
| 必填项 | 字段与证据锚点 | 实现与测试覆盖 | 行列与校验 |
| 登记 | 索引与交叉引用 | 迁移与配置项 | 台账与清单 |
| 验收 | doc-gate | L1 构建 + 相关单测 | 金标 / 逐条对比 |

验收与门禁按改动面选择（`docs/development.md` §验证分层），不默认全量。

## 1. 任务卡（唯一需要填的地方）

| 项 | 值 |
|---|---|
| 目标文档 | `<路径>`（里程碑 master / 实施规格 / 任务表） |
| 本次范围标识 | `<目标文档里定位本次范围的锚：批次号 / 任务号 / 小节>` |
| 上一交付物 | `<上一批产物路径，用作结构参照；不确定就写「自定」——由 Lead 按目标文档的批次顺序自行找出>` |

> **预算不在此卡**：由 Lead 按工作量自估（§4），在检查点 1 连「单元清单 + 步数预算推导 + 预计 $」一起报用户确认。用户不给档位，也不预设上限。
> 目标文档若是里程碑 master：任务状态唯一权威在任务表（见 `docs/milestones/README.md`），计划本体只给范围与验收口径。

## 2. 读什么、按什么顺序读

1. **目标文档**：定位到「本次范围」那一节，读出五样东西——范围、**交付形态**（文档 / 代码模块 / 配置 / 数据 / 规格…）、交付物的名称与位置、验收/强度目标（该文档规定的那一档：L1/L2/L3、金标或等效判据）、**需要同步更新的登记处**。⚠ **形态不统一**：逐条清单 / 表 / 矩阵 / 索引 / 代码与测试 / 迁移与配置 / 数据文件都可能；按读到的做，不许按「N 条」预设。
2. **仓库规则入口**：根 `AGENTS.md`（常驻规矩与红线）→ 命中的子树 `AGENTS.md`（`src/`、`tools/`、`docs/`：写哪、怎么写）；文档标准见 `docs/AGENTS.md`（tier、预算、门禁）；验证、提交与 MCP 见 `docs/development.md`。
3. **团队与单元口径**：`docs/development.md` §团队与委派、§验证分层、§提交与收尾；本任务书用法见 `tools/team-taskbook/README.md`；模板分工见下表。
4. **上一交付物**：结构与口径的参照（同形），但**内容一致性也要核**——本批凡引用它的结论，须回源确认仍是当前有效口径，不得只对形状。
5. 读不到、或两处互相矛盾 → 记 `CR-<本批标识>-n` 并列进「待裁决」，不许猜；非平凡改动按 `.agents/notes/README.md` 同批写 Agent Note。

**模板分工（按时机对号，别漏用）**：

| 模板 | 谁填 / 何时 | 产出落到 |
|---|---|---|
| `batch-contract.md` | 规划单元，P0 规划时（先于任何单元开工） | `.agent-work/<本批标识>/CONTRACT.md` |
| `cell-brief.md` | Lead 派单前，**每个单元一份** | `.agent-work/<本批标识>/units/U-<n>-<角色>.md` |
| `lead-brief.md`（本文件） | 用户交给 Lead，一批一次 | 不产出文件——它是 Lead 的工作标准 |

## 3. 质量底线与工作纪律

### 3.1 质量底线（先于一切成本优化；与 3.2 任一条冲突时，以本节为准）

1. **不删必填内容换绿**：判据、链接、登记行、决策记录、编号只增不减（代码任务等价于删实现、删测试断言、删迁移）；预算触顶按 `docs/AGENTS.md` 的顺序处理（下沉 → 精简 → 提额；提额须同提交改预算并说明理由）。
2. **不省审核**：敌对审核不得跳过、不得压成「自己看一遍」；必须独立会话、输出 PASS/FAIL + 分级 findings，FAIL 必修到 PASS。
3. **不虚报结论强度**：门禁未实现写「待实现」，测试未跑写「未跑」，不把「待核/未验证」写成「已证」；缺哪侧就写缺侧。
4. **到线不是降价交付**：预算到线 → **报一句实测数，继续按标准做**；只有**结构容量**撑不住（单元数超、Lead 上下文超）才拆批次。**任何情况下都不许缩内容**——少取证、少审核、删覆盖项一律算质量事故。
5. **把关是动作，不是签名**：交付前必须亲自**抽检 ≥5 条关键结论**（回源核对或独立复算）+ **逐条看完所有 blocker 级发现**并确认闭环；只看骨架与计数就签 = 未通过把关。
6. **预算不是考核指标**：超预算**不判失败**，准时报数即可；为省预算而少写覆盖项 / 把两项并成一项 / 省掉证据锚点 / 压缩审核 / 把「待核」顶替取证——才算失败，且比超预算严重得多。
7. **不得完全信任子单元的结果**：收到的结果必须**复跑它的验收命令（至少一条）**+ **抽检 ≥1 条结论回源**；只回「PASS」而不给命令与计数的结果，**打回重交**。信任不是默认值，抽检才是。

### 3.2 工作纪律（与内容无关，逐条遵守）

1. **先规划后开工**：按 `batch-contract.md` 产出 `CONTRACT.md`、按 `cell-brief.md` 产出**每单元一份** `units/U-<n>-<角色>.md`（一单元一产物；默认 ≤80 步 / ≤150K、批次默认 ≤8 单元，以 `docs/development.md` §团队与委派为准——**默认值不是硬上限**，可因工作性质调整并写明理由，**不得因预算压力缩小覆盖**；单元下限 = 覆盖其产物声明的全部覆盖项）；每条范围/编号/复用点写成「文件 §小节」或符号锚点，**不写本仓源码行号**；写不出依据的不写。
2. **可以不亲自动手，但先选对承载**（**默认 subagent；teammate 是例外**）：

   | 判断（按顺序问） | 结论 |
   |---|---|
   | 这个角色**只在一个单元里出现** | **subagent**（默认） |
   | 同一角色要**横跨多个单元**（连续审 N 段 / 连续改 N 次） | teammate |
   | 需要与 Lead **来回对话**（追问、裁决、按指令返工） | teammate |
   | 需要在任务板上**被跟踪中间状态** | teammate |
   | 以上都没有 | **subagent** |

   名额与通道（以当前 DSH 运行时为准）：`subagent` 用完就还（并发槽位有限，总量不限），结果由运行时交回或经 `send_message` 汇报；`teammate` 花名册有限（不可删），另有 `wait_agent` 与共享任务板可跟踪中间状态。⇒ 全批 teammate 建议 **≤2**（通常只留「审核」与「集成」）。**等待方式**：subagent 结束时运行时会把结果交回你的会话，其间去做不依赖它的活；**不要 sleep / ls 轮询**（白等 + 空转步，还可能拿半成品就往下走）。某单元没回结果就消失：**重开一个**并写明缺什么，不翻现场猜。同时活跃 ≤5（以 `docs/development.md` §团队与委派为准），本模板取 **≤3**（运营建议，非成本机制）。
3. **敌对审核必做：逐单元、零信任**：
   - **每个单元的产出都要被独立审核**——不是只审最终产物、也不是拿一个整体 PASS 顶掉各单元；审核与作者不同会话。
   - **零信任上游**：审 B 时，A 的产物只是**待核对象**，不是前提；凡被 B 引用／继承的事实，必须回源（原始数据 / 客户端 / 基线）核验。上游错了 → 开**上游返工单元**，不在下游就地掩盖。
   - 终审 PASS 前不得收口；最终报告须含**每个单元**的对抗性审核结论（PASS/FAIL + blocker/major/minor）。审核可交队友做，但**最终把关人是你**，结论由你签。
   - **边界（防无限回归）**：审核单元的产出（findings 清单）不再开审核单元；由 Lead 按 §3.1-5 抽检 + 核对「findings 逐条闭环表」是否真闭环。
   - **返工怎么打**（subagent 结束即消失 ⇒ 返工 = 再开一个新的，沿用原单元号、轮次记 round-2）：任务书三件套 = 原单元交接单（结论/已排除/待办/风险）+ findings 清单（每条给「位置 + 期望值 + 判据」）+ 原产物路径；**只改 findings 覆盖的位置**，清单外问题报告不自行重写；修完重跑该单元验收（改动落到**最终交付物**则加跑仓库门禁）；产物末尾附「findings 逐条闭环表」。**连续 2 轮无实质进展必须停下报用户**。
4. **编号沿用既有体系**：全局号接着上一交付物往下排；按册/按篇（文档型编号）从 01 起的号必须从 01 起；开工前先核一次上一交付物的实际起止，别凭印象。
5. **结构与命名对等**：与上一批产物按**同一组织单位**对齐——文档=章节与子节、代码=模块与文件布局、数据=表与字段/配置=键与取值；**产出单元的分工不得改变该结构**（组织单位随任务类型变，不预设是章节）。
6. **结论强度按最弱一侧取**：一条结论的档位由它最薄弱的那一侧决定，不因其它侧面成立而升级；缺侧记最低档、写明缺哪侧，**级列不升**；证据等级用本仓 L1/L2/L3 与「未跑」标注，不虚高。
7. **记忆落盘**：关键结论与裁决写进 `.agent-work/<本批标识>/`（防上下文压缩丢失）；每个单元结束交交接单四段（结论 / 已排除 / 待办 / 风险），「已排除」不许空。
8. **「登记简化」不是免做许可**：只有「本批范围外 / 技术上不可达 / 需跨批依赖」三类允许登记延后，且必须写明恢复落点；**「太难 / 太费时 / 超预算」不构成简化理由**。不改旧交付物本体——跨篇差异记 `CR-<本批标识>-n` 并报用户，不自行改别人的产物。
9. **队友只专注同一主题**：不同主题开专属队友，避免上下文被无关内容污染。
10. **git 纪律（团队）**：禁用 `--amend` / `add -A` / `reset` / `checkout -- .`，防抹掉别人的提交；**一任务一 commit**（根规则 12），**不 push**；外部参考仓只读（见根 `AGENTS.md` 红线），不动。
11. **体量触碰上限**：按 `docs/AGENTS.md` 的预算流程（下沉 → 精简 → 提额）处理，提额同提交改 `doc-budgets` 并写 Note；不得删必填细节换绿。
12. **结果写结论形**（写进交付物、commit body 或交接单任一）：写「是什么、多少」，不写「第几轮 / 返工 / 自检」这类过程词（文档类产物另受 `docs/AGENTS.md` 禁过程叙述约束）；**结论形 ≠ 省略不利事实**：没做的、没取到的、降级的、有冲突的，必须显式写出来。
13. **验证按「这一步要回答的问题」分组，不按命令条数拆步**：

    | 这一步要回答 | 一个步骤里跑什么 |
    |---|---|
    | 能不能编译？ | 只 `dotnet build Mahjong.sln`（不要顺带跑测试与门禁） |
    | 某个测试类绿不绿？ | 只 `dotnet test Mahjong.sln --filter <该类>`（已 build 过就加 `--no-build`） |
    | 能不能提交 / 收口？ | build → L1 测试 → `pwsh -File tools/doc-gate/doc-gate.ps1 -Fail`，**同一个 `run_code` 里跑完** |

    **禁止两件事**：① 同一个问题的答案拆成多步；② 把不同问题硬塞成一批（中间态跑 doc-gate 必然白红；只改文档却跑 build 是空转）。成本口径：**一步 = 一次完整上下文重发，步骤数才是成本**；L1/L2/L3 是「跑什么、何时跑」的口径（见 `docs/development.md`），不是调用粒度。
14. **状态新鲜**：任务板状态及时变更，让用户和所有成员都能看到最新进展；完成后向用户汇报。
15. **不跑变异，只记台账**：本批**不得执行变异验证**（临时改实现看用例是否变红）——该类验证由用户统一安排时间执行。只把变异点登记进 `docs/reference/mutation-ledger.md`，结果列写「未跑」；汇报写明「已登记、未跑」；**不得声称做过变异验证**，也不得把未变异的用例写成已绿。
16. **产物（交付物）不得带环境绑定**：写进交付物的内容不出现绝对路径、盘符、用户名、本机目录；只说按哪个环境变量或相对路径定位（例：`%USERPROFILE%/.dsh/…`、`$HOME/.dsh/…`）；本仓引用用符号锚点，不写行号。
17. **MCP 与工具通道**：开工先探活（Godot MCP 是硬门禁；本项目 C# 符号 MCP 优先，不可用按 `docs/development.md` 降级并逐处说明理由）；MCP 写操作（改场景/资产/导入）必须属于已确认任务，工具不得隐式触发。
18. **不手改 `content/tables/*.bytes`**：替换/重生成需 Note + 逐条对比（根红线）。
19. **需要先征得同意的操作**：停服/重启服务、结束用户进程、修改场景/资产/外部仓库、MCP 写操作、批量重命名/删除、任何可能不可逆的操作——先停下问用户。

### 3.3 复发即打回的常见错误

| 现象 | 含义 | 正确做法 |
|---|---|---|
| 发给未知成员报 `… not found` | target 不存在或已结束 | 按 `list_agents` 取有效 target；追加任务重开一个并附交接单路径 |
| `sleep N; ls …` 轮询等产物 | 用轮询代替运行时通知 | 结束本回合等通知（`teammate` 才用 `wait_agent`）；先做不依赖它的活 |
| 同一轮把全部单元一次派出去 | 活跃数超出稳定区间 | 默认 ≤3 活跃，分批派 |
| 某单元无产物就往下走 | 半成品被下一棒继承 | 该单元重开补齐；交接单「待办」写清缺什么 |

### 3.4 偷工减料的四个可检信号（交付前自查；也供用户抽查）

| 信号 | 怎么查（不需要懂业务） | 判定 |
|---|---|---|
| **覆盖项少了** | 交付物覆盖项数 vs 契约 §2 范围表（文档=条目、代码=用例与分支、数据/配置=行列与键值） | 少于声明 = 偷工，打回 |
| **必填项或证据锚点缺** | 随机抽 5 项，看必填项是否齐 + 是否给得出「文件 §小节 / 符号 / 测试名 / 命令」级证据 | 缺 ≥1 = 打回 |
| **审核漏单元** | 审核报告是否**逐单元**给 PASS/FAIL | 缺单元 = 漏审 |
| **闭环清单条数不符** | 闭环清单条数 vs findings 条数 | 不等 = 未闭环 |

另：**子单元结果没有「命令 + 退出码 + 计数」凭证 = 视为未验收**（只写「PASS」不算）。

## 4. 预算：**是预报，不是限额**（由 Lead 按工作量自估；用户不给数字、不给档位）

**先做单元分解（§3.2-1），再套公式**——四档只是 Lead 自查量级的参照，不是用户给的指标；分解结果与档位对不上时，以分解为准并把差异写进检查点 1 的报告。

口径（DSH 计费，以实际计费为准）：未命中输入 $0.30/M · 缓存读 $0.006/M · 输出 $1.20/M。

```
单元数 = 规划1 + 采集(按「面」切) + 产出(按交付块切) + 集成1 + 审核1，总计 ≤ 8
步数预算 = 规划50 + Σ采集×70 + Σ产出×70 + 集成75 + 审核60，再加 20% 返工余量
折算 $ = 步数预算 × 0.0055（外部同类批次实测 0.0045~0.0060 的中值；**参照值，未在本仓校准**，首批实测后复核）
```

量级自查（参照值来自外部同类批次的文档型任务）：逐条型 小（≤3 项）≈380 / 中（4–12 项）≈560 / 大（>12 项或多面）≈850 步；表/矩阵型（无逐条清单）≈550 步。**代码实现、缺陷修复、数据整理等其它形态不套档**，按首轮实测校准，偏离 1.5 倍以上说明理由。

**超预算怎么办**：报一句实测数（例：「实测 $3.4，自估 $2.5」），**继续按标准做完**；不需要批准、不需要解释、不需要补救。用户要的是**可预期的规模**，不是不许超。

**超过默认 8 个交付块，优先拆批次**——真正的结构上限是「Lead 会话 ≤150K」，单元数只是经验值；不拆就必须说明为什么撑得住。结构性硬约束（与钱无关）：Lead 会话 ≤150K（超了会丢裁决）；步数/金额只是**报数口径**，不设上限；单单元 ≤80 步 / ≤150K；同时活跃 ≤5（以 `docs/development.md` §团队与委派为准；模板取 3 属运营建议）。**报数点（不是停点）**：收口前用会话日志实测 `$`，超过自估 1.5 倍就报一句，**然后照常收口**；是否拆批次只看结构容量，不看金额。**1.0~1.5 倍之间不是「允许简化」的区间**：只做两件事——继续按标准做、把实测数报给用户；**不许为了回到 1.0 以下砍内容**。

读用量：DSH 会话库中该会话的记录文件 `sessions/<sessionID>.json`（DSH 数据目录 `.dsh/`；Windows 为 `%USERPROFILE%\.dsh\`，其它平台为 `$HOME/.dsh/`；**路径随用户与平台不同，不要写死绝对路径**）→ `record.rows.tokenUsage.val.totals`（`uncachedInputTokens` / `cacheReadTokens` / `outputTokens`）；`$ = in×0.30/M + cr×0.006/M + out×1.20/M`。

**省什么、不省什么**（两边都别搞混）：

| 该省（过程开销，不损质量） | 不该省（交付内容，省了就是质量事故） |
|---|---|
| 同一文件在单元内反复读（>3 次）→ 脚本一次抽全 | 覆盖项数 / 把两项并成一项 |
| 空转步：`sleep` 轮询、「先看一眼再决定」 | 必填项 / 证据锚点 |
| 大输出灌上下文（>2K）→ 落盘，只回路径与计数 | 逐单元审核 / 回源核验（零信任上游） |
| 多个单元各读一遍同一底座 → 一份 briefing 复用 | 证据强度标记 / 「待核」标注 |
| 在胖上下文上续轮 → 换新单元 | 登记闭环（索引 / 边界 / 结果） |
| 逐条抄已有结论 → 引用它 | 结构需要时必须拆批次 |
| 过量并行（同时撞上游故障） | 抽检与把关动作 |

判据一句话：**省掉的应该是「重复劳动」，省不得的是「证据与覆盖」。**

## 5. 检查点：只找用户两次，提交不等审

1. **规划完成**（需用户确认）：发「范围表 + 单元清单 + 步数预算推导 + 预计 $」→ 确认后再派工。
2. **遇到必须用户拍板的**：跨篇订正会影响别人的产物 / 需改旧产物本体 / 返工第 2 轮仍 FAIL / 单元数或 Lead 上下文撑不住（该拆批次）。**超预算不进这张清单**——报数即可，不找用户。
3. **完成后汇报**（通知，不是审批）：提交清单 + 门禁结果 + 遗留项；**提交不需要等用户审**，但**不 push**。

## 6. 完成判据

- **交付结果面向「使用它的人」**：文档可读、代码可运行、数据可取用、配置可加载；给具体值与结论，不写空泛概括（形态以目标文档规定为准）；
- 交付物覆盖本次范围全部覆盖项，必填项齐、空缺显式登记，强度标记按目标档（不虚高）；
- 敌对审核终审 **PASS：blocker 0 且 major 全部闭环**（未闭环的 major 须经用户裁决接受并写明理由），每个单元的审核结论齐；
- 门禁全绿：改文档跑 L2（`pwsh -File tools/doc-gate/doc-gate.ps1 -Fail` 退出 0）；改代码跑 L1（build + 相关单测）；里程碑收口跑 L3（见 `docs/development.md`）；改 `content/tables` 跑金标验证（见 `docs/TABLES.md`）；**只报真正跑过的命令与退出码**；
- 体量 ≤ 登记预算（`tools/doc-gate/doc-budgets.json`）；
- 提交按 §7。

## 7. 提交粒度（本仓：一任务一 commit；禁止压成一坨）

- **一任务一 commit**（根规则 12 + `docs/development.md`）：Conventional Commit，标题 ≤50 字，body ≤10 个非空行（改了什么 / 为什么 / 只写跑过的验收命令）。
- 一个批次含多个任务 → **按任务拆提交**，每个提交自洽且单独过门禁；禁止把多任务压成一个提交。
- 同一提交必须含主体与「少了它就过不了门禁」的配套（预算条目、登记表、生成物登记），否则该提交本身过不了门禁。
- 不用 `--amend`、不压扁已有提交；漏了内容用**追加提交**补；**不 push**。
