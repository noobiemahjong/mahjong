# Agent Note: 设计基线是 DESIGN v1.0，变更走新 Note

Status: implemented

## Problem

`docs/DESIGN.md` 已把目标、分层、tick 引擎、会话流、回放、观战、重连、部署、测试与里程碑写成 v1.0，并用 D1–D18 记录拍板结论。开工前必须回答：谁是设计权威？设计要改时改哪里、怎么留痕？决策理由与设计正文如何不互相复制？

## Decision

1. `docs/DESIGN.md` v1.0 是**设计基线**；D1–D18 与各章节是当前权威。实现必须能指回其中一条，或指回一条显式收窄它的 Note。
2. 变更基线必须写**新 Agent Note**，并写明「收窄/替代 DESIGN §x 或 Dn」；同一提交内更新 DESIGN 决策表（状态列加「被 Note 收窄/替代」）。
3. Note 正文冻结：已发布的 Note 不改写；新决策写新 Note 并交叉链接。
4. 版本只在基线级变更时递增（v1.0 → v1.1 …）；Note 不编号、不建索引。
5. 本仓不与旧 Unity 版做行为等价；冲突以 DESIGN/Note 为准，旧项目只作素材参考。

## Alternatives considered

- **Issue/Wiki 作为设计权威**：与代码不同仓、不可离线、评审不可复现；团队扩到需要多人并行评审时再评估。
- **直接改 DESIGN 不留 Note**：无法追溯，旧结论会被静默覆盖；不重开。
- **把 D1–D18 逐条拆成 Note**：同一信息两份副本，必然漂移；DESIGN 已足够，单条决策需要长论证（>1 页）时才拆。
- **旧 Unity 行为作为基线**：旧版很多设计不合理，会把重写绑死；仅在需要复用某条旧规则细节时查旧代码，不建对照表。

## Consequences

- 「设计改了」的提交必须同时出现 Note 与 DESIGN 变更；只有其一的评审直接打回。
- 里程碑任务若发现设计与实现冲突，先写 Note，再改代码。
- DESIGN 预算 64KB；超出时先判断是「信息该下移」还是「确实需要扩基线」。
